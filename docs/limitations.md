# 已知限制

按"限制 → 影响 → 缓解/计划"写，与 README 的对应段落是同一份内容。

## 1. 提交的评测数字来自确定性参考策略，不是真实大模型

**影响**：表格证明的是"管线 + 工具 + 手册"的贡献与回归稳定性，不是某个具体模型的强弱。
真实模型的数字需要用 `RD_LLM_PROVIDER=openai_compat` 自己跑。

**缓解**：`make eval` 一条命令即可复现；harness 会把策略名、模型名、prompt 版本写进结果
JSON。README 明确标注了这一点，没有把参考策略的数字包装成"模型效果"。

## 2. 沙箱后端的信号比真实集群干净

**影响**：真实集群里指标会缺、日志会截断、事件会迟到，因此真实准确率一定低于 100%。

**缓解**：`make eval-full` 走 k3s；预算收紧实验已经展示了"证据变少 → 准确率下降"的关系。

## 3. kubectl 注入路径没有在真实集群上验证过

**影响**：每个场景都写了 `inject_kubectl`/`recover_kubectl`，但字段标记为
`kubectl_verified: false`；本仓库的 CI 只跑沙箱路径。

**缓解**：`faultlab/runner.py::run_kubectl` 默认 dry-run，必须显式传 `dry_run=False`；
上线前需要在 k3s 上逐条跑通并把这些标记改成 true。

## 4. 只支持 16 类单点故障

**影响**：级联故障、多故障并发、慢演进故障、Redis Cluster 模式都不在范围内
（后者本就是计划里明确不做的）。

## 5. L2 只给建议，不执行

**影响**：改 CR、扩容、改配置这类动作需要人工执行，端到端无法全自动。

**缓解**：这是刻意的安全选择；命令在结论里给出，可直接复制。

## 6. 审批是"单人单次"

**影响**：没有双人复核、没有变更窗口、没有回滚编排；批准即执行。

## 7. 幻觉率只是代理指标

**影响**："引用对不上"能被自动发现，"引用对得上但推理错误"不能。

**缓解**：失败分析文档明确写出这一层缺口，并保留人工抽样作为下一步。

## 8. 知识库是 BM25，不是向量检索

**影响**：同义改写的召回弱于向量模型（例如告警里说"卡顿"而手册写"延迟"）。

**缓解**：分块按"一个现象一块"、标题与症状都进索引，抵消一部分；索引构建与运行时读同一份
JSON，保证可复现。需要向量检索时替换 `tools/kb.py` 的 `KnowledgeBase` 即可，接口不变。

## 9. SQLite + 单副本

**影响**：轨迹库与沙箱都只能有一个写者，Agent 不能水平扩容；`Recreate` 策略意味着重启
期间 API 不可用。

**缓解**：单实例对本场景足够；需要水平扩展时应先把轨迹库换成 Postgres。

## 10. 容器化 k3s 的存储在容器内

**影响**：容器化 k3s 重启后 PVC 数据会丢，长期演示环境不建议用它。

**缓解**：长期环境按 `deploy/cluster/k3s-install.sh` 装在 Linux 宿主机上；`make backup`
和 `docs/runbook.md` 的恢复演练提供兜底。
