# 失败案例分析

数据来源：`eval/results/latest.json` 的 `failures` 字段（每次运行自动归类）。
分类规则写在 `eval/metrics.py::failure_breakdown`：

| 类型 | 判定条件 | 含义 |
|---|---|---|
| 证据不足 | 标准信号没被观察到 | 探针选错了/没看到 |
| 证据未被引用 | 看到了但结论没引用 | 证据到结论的传递断了 |
| 推理错误 | 引用了不存在或对不上的调用 | 幻觉 |
| 类别混淆 | 证据齐全但类别选错 | 判别规则/模型判别错误 |

## 1. A 组：没有工具，只能靠告警措辞

A 组 43.8%。失败样本集中在"措辞误导"：

| 场景 | 标准 | A 的预测 | 为什么错 |
|---|---|---|---|
| S01 | pod_restart | probe_misconfig | 告警里写了"不可用"，纯文本先验更倾向于"未就绪/探针" |
| S03 | maxmemory_reached | oom_killed | 告警里含 OOM 字样，但没有工具就无法区分"容器被杀"和"写入被拒" |
| S07 | auth_failure | network_partition | "复制中断"的措辞把注意力引向网络 |
| S11 | disk_full | max_clients | 告警同时提到"写入被拒绝"与连接数，没有证据只能猜 |

结论：**告警文本不足以定位根因**。A 组的 Top-3 有 87.5%，说明它并非乱猜，
而是无法在候选之间做判别。

## 2. B/C 组：单次采集的覆盖上限

B 组 81.2% 的失败全部来自"第一轮探针集合没有覆盖决定性证据"：

| 场景 | 失败原因 |
|---|---|
| S08 | 单次采集拿了副本 INFO 与日志，但没有 `k8s_get_resource(service demo-headless)`；只能判"链路中断"，判不到"Headless Service 不存在" |
| S13 | 慢日志为空、延迟指标高；单次集合里没有 cfs throttled 指标，只能落到 slow_query |
| S14 | 拿到了链路 down，但没有 `sync_full` 计数，无法把"全量同步风暴"与"网络阻断"分开 |

C 组 93.8%：手册让第一轮把探针花在"手册说该看的检查"上，于是 S08/S14 被补上；
S13 是 held-out（手册里没有 CPU 限流这一类），仍然失败——**这正是 held-out 设计要暴露的**
（如果 C 在 held-out 上也变好，说明出现了泄漏）。

B 组在 S08 上的完整失败实录见 [`demo-failure-trajectory.md`](demo-failure-trajectory.md)
（由 `python scripts/capture_demo.py --scenario S08 --variant B --output
docs/demo-failure-trajectory.md` 生成）：它拿到了 `replica_link_down`，
但探针集合里没有"Headless Service 是否存在"这一项，于是只能给出 `network_partition`。

## 3. D 组：循环补证据后全部命中

D 组 100%（16/16，3 次重复）。它靠的不是更聪明的判别，而是更完整的证据：
平均 10.4 次工具调用，证据召回（已观察）100%。

剩余缺口是**引用率**：已引用 90.6%。也就是说有少量被观察到的信号没有写进结论文本。
这不是错误结论，但会削弱可解释性，是下一步要改进的点。

## 4. 预算收紧：分数来自证据，不来自猜测

把 `max_tool_calls` 压到 3（`eval/results/budget-pressure.json`）：

| 指标 | 完整 D | 收紧后 D |
|---|---|---|
| Top-1 | 100.0% | 81.2% |
| Top-3 | 100.0% | 87.5% |
| 证据召回（已观察） | 100.0% | 43.8% |
| 平均工具调用 | 10.38 | 3.0 |
| 越权次数 | 0 | 0 |

证据收集被砍掉三分之二，准确率随之下降——反向说明完整版的高分来自证据，而不是某个隐藏的
类别映射表。同时它给出一个真实的工程结论：**预算不够时应该少下结论，而不是降低证据门槛**，
当前实现的行为正是把 `budget_exhausted` 写进结论并降低置信度。

## 5. 尚未覆盖的失败形态

- 工具输出被截断导致关键行落在中间（当前实现保留头尾；S02 类故障的 OOMKilled 在事件里，
  但"关键证据正好被截掉"的对照场景还没构造）；
- 两个故障同时注入（例如磁盘满 + 主从断链）时的归因顺序；
- Prometheus 指标缺失/延迟到达时的降级路径；
- 真实模型在长 prompt 下的"引用漂移"（引用正确的 `call_id` 但片段张冠李戴）。
