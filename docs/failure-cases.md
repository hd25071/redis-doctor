# 失败案例分析

数据来自 `eval/results/latest.json` 的 `failures` 字段，分类规则在
`eval/metrics.py::failure_breakdown`：

| 类型 | 判定 | 含义 |
|---|---|---|
| 证据不足 | 标准信号未被观察到 | 探针未覆盖决定性证据 |
| 证据未被引用 | 观察到但结论未引用 | 证据到结论的传递中断 |
| 推理错误 | 引用了不存在或对不上的调用 | 幻觉 |
| 类别混淆 | 证据齐全但类别错误 | 判别规则或模型判别错误 |

## A 组（43.8%）：告警措辞误导

| 场景 | 标准 | 预测 | 原因 |
|---|---|---|---|
| S01 | pod_restart | probe_misconfig | 告警含"不可用"，文本先验偏向探针问题 |
| S03 | maxmemory_reached | oom_killed | 告警含 OOM，无工具时无法区分容器被杀与写入被拒 |
| S07 | auth_failure | network_partition | "复制中断"的措辞将注意力引向网络 |
| S11 | disk_full | max_clients | 告警同时提到写入被拒与连接数 |

A 组 Top-3 为 87.5%：可在候选之间排序，但无法在缺少工具时做判别。

## B/C 组（81.2% / 93.8%）：第一轮探针的覆盖上限

| 场景 | B 的失败原因 | C 是否修复 |
|---|---|---|
| S08 | 已获取副本 INFO 与日志，未检查 Headless Service 是否存在 | 是 |
| S14 | 已获取链路 down，缺 `sync_full` 计数，无法与网络阻断区分 | 是 |
| S13 | 慢日志为空，第一轮未取 cfs throttled 指标 | 否（held-out） |

## D 组（100%）

平均 10.4 次工具调用，证据召回（已观察）100%，已引用 90.6%：
部分已观察到的信号未写入结论文本，属可解释性缺口而非结论错误。

## 预算收紧

| 指标 | 完整 D | max_tool_calls=3 |
|---|---|---|
| Top-1 | 100.0% | 81.2% |
| 证据召回（已观察） | 100.0% | 43.8% |
| 平均工具调用 | 10.4 | 3.0 |

预算不足时，实现的行为是把 `budget_exhausted` 写入结论并降低置信度，而非放宽证据要求。

## 真实集群上的失败形态

沙箱中不出现、真机上出现过的两类（详见 [real-cluster.md](real-cluster.md)）：

- 陈旧事件：Kubernetes 事件默认保留约 1 小时，已恢复故障的事件会让后续诊断误判。
  现按事件年龄过滤，超过 900 秒不作为故障证据。
- 前序故障残留：连续注入多个故障时，前一个故障的残余证据会污染后一个诊断。
  验证脚本会在注入前检查集群健康并清理事件。
