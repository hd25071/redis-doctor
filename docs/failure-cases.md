# 失败案例分析

数据来自 `eval/results/latest.json` 的 `failures` 字段，分类规则在
`eval/metrics.py::failure_breakdown`：

| 类型 | 判定 | 含义 |
|---|---|---|
| 证据不足 | 标准信号未被观察到 | 探针没有覆盖决定性证据 |
| 证据未被引用 | 观察到但结论没引用 | 证据到结论的传递断了 |
| 推理错误 | 引用了不存在或对不上的调用 | 幻觉 |
| 类别混淆 | 证据齐全但类别选错 | 判别规则或模型判别错误 |

## A 组（43.8%）：告警措辞误导

| 场景 | 标准 | 预测 | 原因 |
|---|---|---|---|
| S01 | pod_restart | probe_misconfig | 告警含"不可用"，文本先验偏向探针问题 |
| S03 | maxmemory_reached | oom_killed | 告警含 OOM，无工具时无法区分容器被杀与写入被拒 |
| S07 | auth_failure | network_partition | "复制中断"的措辞把注意力引向网络 |
| S11 | disk_full | max_clients | 告警同时提到写入被拒与连接数 |

A 组 Top-3 为 87.5%：它能在候选之间排序，但没有工具就无法判别。

## B/C 组（81.2% / 93.8%）：第一轮探针的覆盖上限

| 场景 | B 的失败原因 | C 是否修复 |
|---|---|---|
| S08 | 拿了副本 INFO 与日志，没有查 Headless Service 是否存在 | 是（手册提示查 Service） |
| S14 | 拿到链路 down，没有 `sync_full` 计数，无法与网络阻断区分 | 是（手册提示看 sync_full 与 backlog） |
| S13 | 慢日志为空，第一轮没有 cfs throttled 指标 | 否（held-out，手册无此类） |

完整失败实录：[demo-failure-trajectory.md](demo-failure-trajectory.md)。

## D 组（100%）：证据完整带来的提升

平均 10.4 次工具调用，证据召回（已观察）100%，已引用 90.6%：仍有少量观察到的信号没有写进
结论文本，属可解释性缺口而非结论错误。

## 预算收紧

| 指标 | 完整 D | max_tool_calls=3 |
|---|---|---|
| Top-1 | 100.0% | 81.2% |
| 证据召回（已观察） | 100.0% | 43.8% |
| 平均工具调用 | 10.4 | 3.0 |

预算不足时实现的行为是把 `budget_exhausted` 写进结论并降低置信度，而不是降低证据门槛。

## 真实集群上的新失败形态

沙箱里不会出现、真机上出现过的两类（详见 [real-cluster.md](real-cluster.md)）：

- **陈旧事件**：已恢复的 ImagePullBackOff 事件在 1 小时内仍然存在，导致后续诊断误判。
  已通过事件年龄过滤修复。
- **前序故障残留**：连续注入多个故障时，前一个故障的残余证据会污染后一个诊断。
  评测脚本已加入场景前健康检查与事件清理。
